# 双端发布前验收：2026-10-24

关联 [Issue #21](https://github.com/HYX-2024-1020/shixu/issues/21)，依赖 [PR #18](https://github.com/HYX-2024-1020/shixu/pull/18) 与 [PR #20](https://github.com/HYX-2024-1020/shixu/pull/20)。本轮只交付开发分支修正和验收记录，没有发布安装器、上传微信、部署服务器或迁移个人资料。

## 已修正的实际反馈

- Windows 卡片取消鼠标长按门槛，按住移动超过 7px 即拖动；保留静止点击、分组限制、边缘滚动、Escape 取消和排序持久化。触屏保留长按，微信继续采用上下移动按钮与同源排序规则。
- 鲸鱼点击不再充当播放/停止开关。每次点击从头重播 MP3，声音以自然结束为准，移除 3.2 秒截断；离开页面/切换伙伴时停止。微信使用同源 MP3 与原生音频上下文，生成清单检查两端资源；音频初始化放在资料加载之后，原生音频失败不得阻塞角色、草稿和投递，新增失败回归。
- Windows 设置支持遮罩/再次点击页头位置、关闭按钮与 Escape；微信设置再次点击或点返回回到原桶/世界，草稿与筛选保留。
- 微信首页增加 AI 连接入口，说明服务器统一配置、密钥与同步口令的区别，并分别显示整理与事项对话能力；刷新只查状态，不创建计费任务。
- CI PR policy 对产品源码变动要求更新双端能力表，继续检查 PR 双端影响说明与生成副本；这不能自动完成另一端 UI，仍需逐项适配和真实验收。

Electron 音频验收使用实际捆绑 MP3 与原生媒体播放：连续点击 4 次均触发播放，末次超过 3.3 秒仍在播放，并等待自然结束；不是仅模拟 play() 的检查。完整 UI 初跑的旧测试仍在寻找“停止鲸鱼笑声”，按新交互更新该断言后完整 13 套通过。

后续 GitHub Windows runner 的 MP3 播放时钟无法推进，完整 CI 因音频设备依赖失败；不能把本机通过当作 CI 通过。CI 改用真实捆绑 MP3 的 OfflineAudioContext 解码取得原始时长，再用显式时钟适配器验证每次点击重播、不被动画定时器截断及自然时长结束。常规本机运行仍使用实际 HTMLMediaElement 播放；报告记录 audioMode，不将 CI 适配器称为真实发声。另修复旧恢复测试仅等 packet 状态却提前读取异步用量保存的竞态：现在同时等待 packet=error 和 usage=unreported，仍断言模型没有再次调用。未跳过用例或放宽产品结果。

微信原生运行时：用已安装的官方 miniprogram-automator 0.13.0 和独立临时工程，核对唯一标记与空存储后，实际点击首页 AI 连接、读取设置状态并取得截图。后续完整流程遇到开发者工具的 `No context found for objectId 2` / `getPageMetaByWebviewId` 上下文错误，尝试重新建立工程与重新取上下文仍未完成，因此本轮 **不把原生完整交互或原生音频记为通过**。Computer Use 检查窗口时也未取得可核验的隔离工程画面，未继续操作原工程。没有提交不可稳定复现的自动化脚本；完整原生回归和手机验收保留为待办。

临时工程只复制 Git 明确跟踪的工程文件和本轮音频，增加唯一标记并核对空存储；没有复制 project.private.config.json，没有清理旧工程存储，也没有关闭域名校验。Node 24 不能直接 spawn .bat 的测试启动问题已用官方 CLI 启动后连接 SDK 的方式排除，不属于产品故障。截图和工具日志仅作为诊断，不能替代验收通过。
