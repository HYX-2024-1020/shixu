# 拾序电脑版改造任务清单

记录日期：2026-10-23。状态：0.3.1 已按用户提供前端完成卡片与投递材料交互改造；首版主体及真实模型样本已通过，原生来源拖拽仍待独立实测。最新交付与安装状态见 HANDOFF.md。

本文件是后续分批改造的依据。2026-10-23 用户已明确要求开始实施；此前仅更新文档的限制已被新的开始指令取代。新对话先读根目录 HANDOFF.md，再读本文件；用户明确开始后按阶段实施。下文复选框表示实施状态，不代表需求是否已确认。

## 1. 产品目标与边界

用户把杂乱的文字、图片、文件、老师通知和附件交给拾序；拾序负责接住、理解、分类，给出明确结果，并让用户轻松管理后续事项。

核心体验：输入省事，结果清楚，轻重缓急一眼可辨，界面简单、有新意、不烧心。

已明确要求：

- 电脑版必须是独立的软件，启动后进入应用窗口，不能打开浏览器网页。
- 文字、图片、文件都能拖入；图片识别、压缩包内容读取属于主体能力。
- 两个主要工作区：“投递桶”和“整理结果”，不能把所有内容堆在一个页面。
- 每次整理后给出完整、清晰、显著的反馈，不要求用户自己翻记录确认。
- 整理结果按内容分类；有内容才出现该类别；少而清楚，可折叠。
- 支持正常的事项管理：状态、删除、最近删除、排序、重要程度，以及完成内容的整理。
- 清楚区分原文、AI 总结、AI 建议。
- 弱化每条消息的费用展示；更换当前单调的绿色视觉风格。
- 手机端消息导入和“大肥鱼吃内容”创意先记录，主体完成以后再做。

## 2. 现状核查

依据：README、package.json、桌面启动脚本、BucketApp、PacketCard、GroupCard、files 和共享整理引擎的数据定义。这里是源码层面的核查，未做本轮运行验收。

| 领域 | 当前情况 | 改造差距 |
| --- | --- | --- |
| 桌面运行 | React/Vite 网页；启动脚本启动开发服务后打开网址 | 缺少独立桌面安装包及完整桌面生命周期 |
| 输入 | 有文字输入、文件选择、基础文件拖入和剪贴板文件入口 | 需统一文本/图片/文件投递，验证 QQ、微信实际拖拽行为 |
| 文件理解 | TXT、MD、CSV、DOCX 正文、文字型 PDF | 缺少图片识别、扫描件 OCR、作为输入的压缩包解析 |
| 分类 | 数据类型为 task、idea、habit、note | 缺少通知等类别与清晰的分类浏览工作区 |
| 状态 | 投递处理状态与任务完成勾选已存在 | 缺少完整的事项状态、优先级和面向用户的排序体系 |
| 删除 | 有删除逻辑及 deletedAt 字段 | 不能视为已经具备最近删除、恢复、保留策略 |
| 来源与建议 | 已有 facts、summary、nextSteps、evidence、uncertainties | 需统一展示层级并强化整理回执和来源定位 |
| 关联 | 已有跨投递分组、去重、拆组逻辑 | 新分类、状态、删除恢复不得破坏这些能力 |
| 费用 | 输入附近累计费用、单条卡片费用、用量面板 | 费用退出主要阅读路径，后台记录保留 |
| 数据 | 本地浏览器存储，另有可选个人服务 | 需设计桌面数据落盘与备份恢复；用户确认无需迁入旧测试记录 |

工作区已有 vite.config.ts 修改及未跟踪的桌面启动脚本；后续实施须保留并核查这些既有工作，不擅自覆盖。

## 3. 详细任务与验收条件

### D01 独立桌面软件（主体必做）

- [x] 首版只做 Windows，已完成独立应用构建和本机安装验收；0.2.1 补丁发布构建亦通过回归。
- [x] 已选择 Electron 并完成独立运行验证；取舍、后续文件路线见 desktop-implementation.md。
- [x] 提供可安装、独立窗口启动的发布构建；正常使用不要求用户启动终端或开发服务。
- [x] 点关闭缩到托盘继续处理；托盘提供重新打开和明确退出。不做全局快捷键呼出；首版不默认开机启动。
- [x] 设计本地附件存储、密钥存储、升级迁移与备份恢复。
- [x] 用户确认旧记录均为测试，无需做旧网页数据迁入。新软件仍需数据持久化与备份恢复；本轮不删除旧数据。

验收：双击应用进入独立窗口；重启后资料与处理进度可恢复；不弹浏览器；可在目标系统安装运行。独立软件不等于必须重写成原生控件，但交付体验必须满足上述要求。

### D02 统一投递入口（主体必做）

- [x] 支持输入/粘贴文字、拖入文字、拖入图片、拖入文件、多文件选择、截图粘贴。
- [x] 混合文字和附件先积攒在草稿中，用户点“丢进去”后再作为一次投递整理；拖入不自动提交。
- [x] 投递前展示已接收的文字、图片缩略图、文件名和可移除入口，草稿自动保留。
- [x] 拖入时提供清楚的落点反馈；拖拽不能导致文件在浏览器或其他窗口被意外打开。
- [ ] 验证资源管理器、QQ、微信来源的拖入；区分真实文件、临时文件、图片、文字、链接和不支持的拖拽载荷。
- [x] 对来源应用未提供可读取内容的情况给出具体原因和粘贴/保存后拖入的替代入口，不假装成功。
- [x] 评估重复投递提示，允许用户明确保留重复内容。

验收：混合输入不丢字、不丢附件；复制或拖入成功后能立刻看见接住了什么。QQ/微信兼容性必须实际测试，不能从普通文件拖入成功推断。

### D03 图片理解（主体必做）

- [x] 至少覆盖常见截图和照片格式，具体范围实施前确认。
- [x] 提取通知截图、纸面拍照材料等文字；扫描 PDF 纳入同一识别链路。真实调用通过通知图、扫描通知和公开中文手写纸面图片；未以模拟接口代替。
- [x] 图片范围包含手写、表格、公式和布局理解；已以中文手写诗文及通知表格/公式做真实样本核对，复杂材料仍需对照原图，不承诺全部准确识别。
- [x] 将图片识别结果与同次文字、附件联合整理，保留原图和定位信息。
- [x] 低清晰度、识别不全、无文字、内容冲突必须明确反馈，允许补图或修正识别文字。
- [x] 首选复用用户填写的 DeepSeek API key 接入官方视觉模型；实现时验证模型选择和图像请求格式，不额外要求另一家服务密钥作为首版前提。

技术核查（2026-10-23）：[DeepSeek 官方图像理解文档](https://api-docs.deepseek.com/zh-cn/guides/vision/)已说明 deepseek-flash 支持文本与图片混合输入。现有文字提取链路仍需改造，填过 key 不代表当前应用已发送图片。本轮仅核查公开文档，未调用用户密钥。后续开发时重新核对模型能力、限制与价格。

验收：只投一张老师的通知截图，也能得到有来源依据的结果；识别不出的日期和要求不能编造。

### D04 压缩包读取（主体必做）

- [x] ZIP、RAR、7z 均纳入目标范围；用户材料也包括 Word、PDF、图片、Excel、PPT、代码。建立逐格式读取与失败反馈矩阵，不把“都有”理解成支持所有二进制格式。
- [x] 纳入 DOC/DOCX、XLS/XLSX、PPT/PPTX 的读取或转换路线验证；代码只作为文本理解，不执行。加密/分卷/嵌套包先验证能力，首版至少可识别并明确解释未处理原因，不能静默忽略。
- [x] 展示包内目录、可读取文件和不可读取文件，保留压缩包及内部相对路径。
- [x] 对支持的内部文件提取文字/OCR，再与投递文字联合理解。
- [x] 针对大量文件分阶段处理，明确已处理、跳过、失败的清单。
- [x] 设置解压体积、文件数、嵌套层数与处理时限；防止路径越界，不执行包内程序。
- [x] 加密、损坏、不支持和超限时提示具体原因；部分成功不能显示成全部成功。

验收：一段“按附件要求完成作业”的文字加一个多文件压缩包，能够提炼对应要求，并定位到包内具体文件。所有未读内容均有说明。

### D05 两个主要工作区（主体必做）

- [x] “投递桶”：输入、草稿、当前队列、本次整理回执。
- [x] “整理结果”：分类浏览、轻重缓急、检索筛选、完成归档与最近删除。
- [x] 两个入口始终容易找到；切换保留草稿、筛选和阅读位置。
- [x] 投递区提供“查看这次整理出的内容”，直达对应结果而不是让用户自行搜索。
- [x] 设置、用量等低频内容放到次级入口。

建议：使用两个稳定的主导航入口；类别采用紧凑列表或标签及数量，溢出时折叠。具体形态由原型验证，不机械套用大量横向标签页。

### D06 强反馈与可追踪的整理过程（主体必做）

- [x] 分清“已接收并保存”“正在读取/识别”“正在整理”“完成”“部分完成”“失败”。
- [x] 整理完成后留下持久可见的回执，不仅弹一个很快消失的提示。
- [x] 回执列出本次新增/更新/合并的事项、分类去向、关键要求、日期、重要程度依据和待确认项。
- [x] 显示附件读取覆盖情况、未读文件及原因；提供就地修正、重试失败部分和查看来源入口。
- [x] 自动关联旧事项时明确指出关联到哪里，提供撤销或拆开入口。
- [x] 批量结果采用整体概览加可展开明细，兼顾完整与易读。
- [x] 处理期间可继续投递；关闭重开后仍能知道上一批结果。

验收：用户不离开当前回执，就能回答“接住了什么、归纳成什么、放在哪里、有没有遗漏、下一步做什么”。例如“新增 2 个任务、1 条通知；2 个附件已读取，1 个文件未能读取”，再列关键结论。

### D07 自动分类与渐进展示（主体必做）

- [x] 已确认初始分类：任务、日程/活动、灵感、习惯、通知、资料/笔记、其他。
- [x] 只有实际出现内容的类别才显示；空类别不占据导航。
- [x] 由模型依据明确的分类规范整理，用户无需投递前选类别。
- [x] 一次投递允许拆出多个类别：通知保留消息背景，任务提取实际行动，并互相关联，避免无意义重复。
- [x] 对无法判断的内容使用“其他”或待确认提示，不任意制造大量新类别。
- [x] 允许用户更正分类，后续自动处理不得无提示覆盖人工修改。
- [x] 类别与状态、重要程度、课程/项目分组分开，避免导航无限膨胀。
- [x] 支持按课程/项目聚合和用户手动建组、移组、拆组；默认平铺事项卡片。分组为可选辅助，不显示“未分组”或催促补组；进入分组直接看到展开的事项。

验收：任务、习惯、灵感、通知能独立找到；只出现两类内容时只展示相应类别；完成内容仍保留原类别。

### D08 状态、排序、重要程度与完成归档（主体必做）

- [x] 首版任务状态采用待办、进行中、已完成；其他状态按必要性后续扩展，不再为常规取舍反复询问用户。
- [x] 日程显示发生时间、是否已结束等合适状态，不把所有内容强套为待办。
- [x] 灵感采用保留/推进/归档等合适动作；通知采用已读/归档；具体命名在交互设计时收敛。
- [x] 习惯只做简单手动打卡，由用户点一下触发，不自动打卡。默认显示累计坚持天数，可辅以连续天数；按本地自然日去重，一天多次点击不多计，误打可撤销。无需复杂周期目标或惩罚机制。
- [x] AI 先判断基础重要程度，用户可修改；提供独立星标和置顶。截止日期越近，默认排序权重越高，到期/逾期明显可辨；重新打开和跨日时更新，不修改原始截止日期。
- [x] 默认排序建议：置顶 → 逾期/临近 → 重要程度 → 其他；同序项保持稳定，用户可切换排序。
- [x] 提供按截止时间、重要程度、创建时间与自定义顺序排序；自定义顺序支持手动调整。用户选自定义排序时尊重其顺序，日期紧迫性仍显示在卡片上。
- [x] 今日、即将到期、逾期以筛选视图呈现，不再新增内容类别。
- [x] 完成内容移入可检索的完成视图，按原类别/项目组织，记录完成时间，可撤销完成。
- [x] 支持编辑标题、分类、时间和重要程度；保留原始来源。
- [x] 分组项目与子项的完成逻辑明确：部分完成不等于整组完成。

验收：用户能快速识别最先要处理的事项，知道哪些已完成，并可改错；同一来源产生的任务可独立完成，不影响其他事项。

### D09 删除、最近删除与恢复（主体必做）

- [x] 所有类别（包括习惯及打卡记录）与文件附件均支持删除和最近删除；明确区分删除事项、删除整次投递和删除原始附件。
- [x] 提供短时撤销入口与最近删除列表；记录删除时间、来源和可恢复范围。
- [x] 恢复时处理类别、状态、分组关系和附件引用；恢复原分组不可行时说明原因。
- [x] 共享来源仍被其他事项引用时，不因删除一个事项而破坏其他事项。
- [x] 最近删除保留 30 天，到期自动清理；页面显示剩余保留时间，并允许提前永久删除。应用未运行时，启动后补做过期清理。
- [x] 清理覆盖无引用原文件、压缩包解压副本、缩略图和识别缓存；共享文件按引用检查，只要仍被有效内容或保留期内内容使用就保留。移除共享附件需清楚展示影响范围。
- [x] 为后续服务器存储预留统一保留策略、空间统计与可重试清理机制；当前不部署云端。未来使用服务商文件上传存储时也须设置过期或删除策略。
- [x] 永久删除有明确操作含义；原文件、整理结果与计费记录的保留关系需说明。

验收：删除后在最近删除可找到并恢复，恢复内容可用；不能误删其他仍在使用的原文件。

### D10 原文、总结、建议的清晰分层（主体必做）

- [x] 卡片默认展示标题、关键结论、必要日期/状态及来源入口。
- [x] 明确区分“AI 总结”“原文要求”“AI 建议”“待确认”，不只依靠颜色区分。
- [x] 原文要求可定位到原始文字、图片或文件位置；识别转写与原图不能混为一谈。
- [x] 原文硬性要求不能被建议覆盖；建议不能自动变成用户承诺或老师要求。
- [x] 总结不确定、来源冲突、缺少日期时就地说明，支持用户确认和纠正。
- [x] AI 建议按需展开，可采纳为行动；采纳后仍记录它来自建议。
- [x] 长原文和附件分层展开，减少默认页面负担；无需在多个页面之间来回核对。

验收：用户一眼能区分“原消息说的”“模型归纳的”“模型建议我做的”。

### D11 模型整理规范（主体必做）

- [x] 明确结构化输出：类别、标题、摘要、原文事实、行动要求、日期依据、来源引用、建议、不确定项。
- [x] 规定拆分、去重、关联、通知转任务、习惯识别和其他类别的边界。
- [x] 日期记录投递时间与时区；模糊日期不强行填写；原文冲突保留双方依据。
- [x] 重要程度缺少依据时不强行断言，允许建议但必须标记。
- [x] 文件和图片中的内容只作为待整理资料，不能修改应用规则或触发自动执行。
- [x] 长材料、图片和压缩包拆段后仍保留来源映射和覆盖清单。
- [x] 重试不重复生成事项；重跑不得覆盖人工确认的内容而无提示。
- [x] 用代表性材料检查完整性、分类合理性、日期准确性和建议边界；真实样本覆盖六类内容、绝对/相对日期、模糊日期、建议与附件指令边界。报告见 release/live-validation.json 与 release/live-acceptance.json，不据有限样本宣称通用准确率。

### D12 新视觉与费用降噪（主体必做）

- [x] 已选定“有角色感、轻松活泼”的视觉方向，放弃当前大面积单调绿色；具体配色、字体、圆角与轻动效由实现者设计，不再重问风格方向。大肥鱼复杂动画仍留后期。
- [x] 用字体层级、留白、少量强调色和轻量动效提升辨识度；不能只换主题色。
- [x] 默认界面保留高频动作，详细信息逐层展开；支持小窗口、长标题和大量结果。
- [x] 重要状态用文字/图标/层级共同表达，不依靠满屏高饱和色。
- [x] 去掉单条卡片中抢眼的费用强调；模型和费用留在设置或次级统计入口。
- [x] 保留真实用量统计及待核对状态，视觉弱化不等于停止记账。

## 4. 后续创意池：本轮不实施

## 6. 实施顺序与阶段验收

1. **交互草图与技术验证**：关键需求已确认；按本清单产出关键界面原型，验证桌面框架、DeepSeek 视觉与文件解析路线，无需重复询问已回答问题。
2. **桌面与数据基础**：独立应用、托盘、持久化、备份恢复、事项身份及状态模型。确保后续删除、恢复、关联不依赖易变的数组位置；无需旧数据迁移。
3. **输入能力**：统一拖入与粘贴、OCR、压缩包、进度与覆盖反馈。用真实来源场景验证。
4. **整理与管理闭环**：两工作区、分类、强回执、来源/建议分层、编辑、排序、完成、删除恢复。
5. **视觉完善与发布验收**：在既定视觉方向下打磨动效和密度，测试恢复、离线、托盘、重启、30 天清理、长内容及 Windows 安装包。
6. **后续增量**：大肥鱼动画；手机消息导入另立实施阶段。

每阶段完成后更新本文件复选框和验证记录；未验证项不能写成已完成。这里不预估工期，待范围与技术验证完成再排。

## 7. 代表性端到端验收案例

| 输入/操作 | 应有结果 |
| --- | --- |
| 只有一张老师截图 | 识别文字、提炼要求和日期、保留原图；模糊处明确提示 |
| 一段通知 + 含图片和文档的压缩包 | 联合理解，列出读取覆盖情况，定位包内来源 |
| QQ/微信拖入与粘贴 | 支持的载荷可用，不支持的载荷有明确替代操作 |
| 混合任务、灵感、习惯与通知的一段话 | 分出合理事项，类别只按已有内容出现 |
| 新通知修改旧作业截止时间 | 回执显示更新及依据，保留原文，可纠正误关联 |
| 多项任务一项完成 | 仅该项完成，组内其余任务仍在；完成视图可查 |
| 删除并恢复共享同一附件的一个事项 | 恢复正常，其他事项和原件不受损 |
| 半数文件读取失败 | 明确部分完成和失败明细，不报全部成功 |
| 处理途中断网、退出再打开 | 原输入完整、进度可恢复、不重复产出 |
| 对模型分类和日期作人工修正 | 修正立即生效，后续处理不悄悄覆盖 |
| 打包安装、关窗与重开 | 独立窗口、无开发依赖、关窗进托盘，处理继续 |
| 同一习惯一天点多次，随后删除并恢复 | 当天只记一天，累计天数正确，恢复含打卡历史 |
| 截止日期逼近或跨日 | 默认顺序自动更新，星标/置顶/自定义排序语义清楚 |
| 最近删除满 30 天 | 无引用原件和衍生文件被清理；共享有效附件仍可用 |
